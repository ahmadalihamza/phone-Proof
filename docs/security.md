# Security

Implemented: Argon2id passwords; 15-minute JWT access tokens; hashed opaque rotating refresh tokens with reuse-family revocation; server-controlled roles; object ownership checks; optional admin TOTP with encrypted seeds, accepted adjacent time steps and replay prevention; input size/type restrictions; contextual Android permissions; encrypted Keystore token storage; no Android backups; production HTTPS configuration checks; Redis rate limiting that fails closed in production; private media; SHA-256/Ed25519 signatures; append-only DB triggers; server financial pricing and entitlement decisions.

Production requires PostgreSQL, Redis, HTTPS public URL, explicit hosts, private S3 and a provisioned signing key. Development payments are rejected in production even if requested by a client. Generate secrets outside source control. Keep signing keys and MFA_ENCRYPTION_KEY in the host secret manager. Restrict trusted proxy IPs explicitly; never accept spoofed forwarding headers from arbitrary clients.

Payment orchestration now verifies provider reference, transaction identity, Decimal amount and currency independently of callback data. Authenticated callback events are time checked and deduplicated; pending or rejected verification is retryable and does not allocate quota. Financial terms, assigned references/timestamps and append-only payment events/receipts are guarded in the ORM and database. User receipts are owner protected; refund approval/rejection uses admin RBAC/MFA. Release Android hides development settlement controls. No real merchant authentication/collection protocol or credentials are configured, so the orchestration is not a certified Easypaisa, JazzCash or card integration. See payment-readiness.md for production gates.

Provision an admin interactively: `python -m app.provision_admin admin@example.com` from backend. It refuses to overwrite an existing user, asks for a password and outputs an authenticator enrollment URI once. Do not paste this URI into tickets or logs. Production admin login is blocked without enrolled MFA. Admin interface is `/admin`; every API operation independently checks its role. Refresh the page/sign in again after the short access session expires.

Report signing uses Ed25519 over raw bytes of the SHA-256 digest of sorted-key compact UTF-8 JSON. Owner report API exposes its canonical payload; the public API returns a privacy projection with a flag indicating that it is not the canonical signed payload. Online verification recomputes and validates the stored canonical report. Public keys must be distributed through the trusted HTTPS service; key rotation needs an operational key registry/retention procedure.

Open gates: Play Integrity server attestation, independent penetration test, organization RBAC/delegation, deployed dependency/container scans, monitoring alerts, production backup/restore and a merchant-certified payment adapter. Signing is evidence integrity, not proof a malicious client ran genuine hardware tests. No root/security bypass is used.

Account recovery uses hashed single-use codes, a 30-minute lifetime, resend cooldown and an encrypted transactional email outbox. Recovery requests disclose neither a code nor account existence. Password reset revokes refresh sessions and advances the user's session version, invalidating previously issued access tokens. Administrator recovery also requires an unused TOTP code. Email verification is bound to the signed-in user. Mail payloads are cleared after delivery, cancellation, expiry or permanent failure; no code or SMTP exception text is logged. The mail worker verifies TLS and never simulates delivery when SMTP is unavailable. Production PostgreSQL concurrency and real staging-email delivery still require acceptance tests.

The 18 October dependency audit identified two advisories in the previous PyJWT 2.14.0 pin. The project now pins 2.15.1, which includes the upstream fixes documented in the [official PyJWT changelog](https://pyjwt.readthedocs.io/en/stable/changelog.html#v2-15-0). HTTP regression tests cover malformed signed `exp`, `iat` and `nbf` claims returning 401 rather than an unhandled server exception. The application continues using an explicit HS256 algorithm allowlist, issuer and audience validation; it does not introduce a JWKS trust flow.
